# 把实验代码做成可信的工程

训练项目的工程质量不看文件数量，而看别人能否知道**运行了什么、结果意味着什么、失败时能否定位**。以下规则可以直接用于本仓库，也适用于后续扩散模型项目。

## 1. 先定义口径，再写数字

`batch_size` 在这里是**每个进程的一次 microbatch**。一个完整窗口在无尾批时的全局样本数是 `batch_size × grad_accum_steps × world_size`；尾窗口和末批不足时应报告实际值。`step` 至少可能指 dataloader 批次、参数更新、训练样本数，不能混写。学习率调度以尝试的参数更新窗口计数。梯度缩放器若检测到非有限值，可能跳过实际更新，所以日志里的 `global_step` 不能单独证明参数确实变化。

报告实验数字时，同一行交代：数据集版本和切分、模型与配置、设备和精度、随机种子、测量次数、指标定义。显存要区分 allocated 与 reserved、当前值与峰值；时间要区分数据加载、训练、推理、首次运行与预热后运行。先固定比较条件，再改变一个变量；不要用一次最佳结果代表稳定收益。

## 2. 测试应能抓住你担心的错误

| 目标 | 弱测试 | 强测试 |
|---|---|---|
| 梯度累积 | 数 `optimizer.step()` 次数 | 同初始化、同样本，比较真实大 batch 与累积后的参数张量 |
| 断点续训 | checkpoint 文件存在 | 连续训练与保存后恢复做配对比较，并说明逐位成立的设备和模型条件 |
| DDP 省通信 | 程序能跑完 | 跟踪 forward 是否在 `no_sync` 中，必要时记录集合通信次数 |
| 学习率调度 | 打印了一条曲线 | 手算短序列每次更新的 lr，并覆盖尾窗口 |
| 性能优化 | 某次运行更快 | 预热、重复测量、同步计时、同时检查结果正确性 |

有一个实用的反证方法：暂时删掉被测逻辑或替换成明显错误值，测试应失败。如果仍然通过，测试只验证了外围现象。破坏实验只在独立副本或分支做，结束后检查文件差异和测试状态。

## 3. 调试按“缩小变量”推进

1. 保存失败命令、完整异常、配置与软件版本；不要只截最后一行错误。
2. 把问题缩到最小输入：例如 7 个样本、batch=2、accum=4，比跑十个 epoch 更能看出尾批错误。
3. 写出**错误输出与正确输出的差**。问的是“从哪一步开始偏离”，不是“调哪个学习率能掩盖”。
4. 每次只改变一个解释变量。固定 seed 不等于自动控制了数据切分、模型初始化、进程数量和内核非确定性。
5. 修完重跑最小复现，再跑相关回归，最后才跑全套测试。

遇到 GPU 问题，先检查 `torch.cuda.is_available()`、设备索引、张量所在设备和 dtype；再检查是否在 autocast 中、是否忘记 `unscale_()`、是否有 NaN/Inf。遇到 OOM，先看显存峰值何时出现、是否有张量被列表或日志长期引用，再考虑减 batch、累积或检查点。不要先堆显存开关。

## 4. 可复现有层级

- **能重跑**：依赖、配置和命令齐全，能得到合理结果。
- **数值接近**：固定数据与种子，明确容差、设备和随机波动。
- **逐位一致**：同一确定性执行条件下，每个权重位完全相同。这是更强的承诺，需要专项测试。

本仓库原有的 CNN 端到端逐位续训测试在当前 Windows CPU/PyTorch 环境下会出现极小漂移，未改动的原版也能复现这一现象。因此精确回归测试现在用较小的 MLP 隔离“状态有没有完整恢复”；CNN 与其他设备的逐位承诺仍需单独验证。不要因为一个近似相同的 loss 就宣称逐位一致，也不要因为微小漂移就不查是否漏存状态。

## 5. Git 与协作习惯

每次改动只解决一个能描述清楚的问题：先复现，再改代码，再补验证，再改文档。提交信息写“改变了什么、为什么”，例如 `fix: normalize partial accumulation windows by sample count`。提交前查看文件清单，检查缓存、权重、数据、私有路径和凭据没有进入提交。不要靠一次性加入全部文件来省检查时间。

README 面向第一次看到项目的人：首屏给问题、结果、三条命令和限制；深度推导放在 `docs/`，并从 README 链过去。代码注释解释“为什么”和“不成立的条件”，不要逐行复述 Python 语法。函数最好有明确输入、输出和状态变化；测试名能读出守护的不变量。

## 6. 本周练习

1. 找到 `src/train.py` 中所有会改变模型或优化器状态的语句，按执行顺序列出来。
2. 把 `test_accumulation_matches_real_batch_even_with_short_last_batch` 的数据改成你设计的另一组尾批；先手算窗口大小与分母。
3. 暂时把 `optimizer_steps_per_epoch()` 改成整除，指出哪个测试应先失败。
4. 给一次训练写四行实验记录：命令、环境、预期、实际。把“代码跑了”改写成可核验的结论。

能独立做完这些，再进入 checkpoint 和 DDP 深挖。每碰到新工具，先问它解决了哪个具体瓶颈，再决定是否加入项目。
